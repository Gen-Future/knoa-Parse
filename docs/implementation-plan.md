# Knoa Parse 完整实现方案

版本：2026-10-15 第二次修订。依据 [横向模块调查](research/2026-10-15-module-selection.md) 与 [ADR 0004](adr/0004-selective-module-integration.md)。本方案替代此前预设 Docling + RAG-Anything 两条主线的安排。当前已实现六种后缀的初始原生路径，并完成 Python 3.12 锁定、依赖审计和合成文档验收。选型不等于已通过集成验收。

## 1. 目标与范围

Knoa Parse 把文件变成结构化、可定位、可核对完整性的证据。统一 API 与 CLI 对接 Knoa 或其他产品，首版单机单实例。首批文档能力逐格式开放，随后加入外部文档分析、音频和视频；不建设独立解析 UI。

只承担输入探测、格式结构、自然单元划分、必要外部识别/理解、来源与派生关系、结果导出。不承担 embedding、检索切块、知识图谱、Agent 编排、长期记忆、资料爬虫或推理服务部署。

首批目标后缀为 `.txt`、`.md`、`.json`、`.csv`、`.tsv`、`.docx`、`.pptx`、`.xlsx`、`.pdf`，且 PDF 先开放原生提取目标。图片、音频、视频随对应服务与阶段开放；catalog 中其余后缀继续保留规划状态，不因同一家族首个格式通过而整体启用。

OCR、ASR、视觉、版面/表格、公式识别、神经 VAD/说话人模型全部外接。简单图片处理、原生格式读取、媒体编解码、规则场景检测允许本地执行。外部服务先实现接口与 mock，真实服务采用时另做效果和成本验收。

## 2. 明确的技术选择

推荐 Python 3.12、uv、单一 Python 项目与一个依赖锁。API 用 FastAPI/Pydantic，HTTP Provider 用 httpx，CLI 先用标准库 argparse；SQLite 存任务和索引，本地目录存原件及派生产物。首批直接依赖已按本地验证版本写入 pyproject.toml；完整 uv.lock 已生成，按不同可选组安装和验收。

一个 API 进程加一个本机 worker，由 worker 启动受限子进程处理任务；CLI 直连同一应用服务层，本地执行时使用同一任务租约，不另写解析逻辑。初始 worker 并发为 1，可配置；不提前引入 Redis、Celery、Kafka 或多个解析微服务。

C/C++ 原生扩展、FFmpeg 等可作为发行依赖，不要求业务代码全是纯 Python。首版不维护自建 Rust wheel、JVM 服务或外部项目完整 fork；跨语言是否可接受，以发布与运维成本判断。

## 3. 模块选型与接入边界

| 模块 | 采用方案 | 接入入口/产物 | 排除与补充 |
| --- | --- | --- | --- |
| DOCX / PPTX | Docling 对应 backend + SimplePipeline | 内部 DocumentConverter 适配；完整 DoclingDocument、图片与 Knoa 映射 | 不复制 backend 源码；不带模型/Serve/全部渲染。源节点与形状定位不够时作有限补充，验收前不假定完整 |
| XLSX | Docling 区域/表格组织 + 原始单元格补充 | 工作表与区域结构；单元格原值/类型/公式/缓存/格式/隐藏 | 不自建表格分区算法；不计算公式。补充读取复用已有 openpyxl 依赖 |
| 原生 PDF | Docling NativePdfPipeline | 原生文本单元、页面、图片、区域、页级状态 | 不包含复杂阅读顺序、标题/表格恢复；这些目标交给外部文档分析 |
| TXT / Markdown / JSON / CSV | 标准语法读取；Markdown 复用已选引擎可用路径 | 原文跨度、节点/记录、结构块 | 不为简单格式引入第二个综合框架；源码文本不执行、不建语义代码索引 |
| 图片 / 扫描 PDF | 必要解码/渲染 + 外部 OCR 或文档分析 | 文字、区域、结构及识别来源 | 不装本地 OCR，不把 Vision 自由描述当精确 OCR |
| 音频 | FFmpeg/ffprobe + AsrProvider | 音轨、分段、转录、时间映射 | 不装 Whisper、神经 VAD、MoviePy；长音频按服务上限确定分段 |
| 视频 | FFmpeg/ffprobe + PySceneDetect 的规则检测器 + 外部服务 | 场景、帧、音轨、字幕、时间关联 | 不搬 RAG-Anything 视频处理器；不引入剪辑/报告产品。检测和真实时间映射分别验收 |
| 网页快照 | 已选 Docling HTML 路径；正文目标按需 Trafilatura | 完整结构与可选正文派生视图 | 两条路径不默认重复执行；不抓网页、不启用浏览器、不保证清洗后 DOM 无损 |
| 电子书/邮件/归档/旧 Office | 后续按实际格式开放 | 优先复用已选引擎的可用 backend；附件走子任务 | 不因目录存在就安装 Tika、Calibre、LibreOffice 或所有格式包 |

RAG-Anything 当前只借鉴上下文与模态关联设计，不安装、不复制源码、不形成必做迁移任务。Unstructured、MarkItDown、MinerU、Marker、Kreuzberg/Xberg、DocVortex、Tika 不进入首版默认依赖；各自拒绝或延后的证据见调查报告。

### Docling 的安装和执行范围

实验基线为已发布的 `docling-slim==2.139.0`，来源提交 `6b77e54c8c83ac46c9c0aa126e2761f57c93e44e`。这是可复现候选，不是最终生产推荐版本。

按阶段显式选择 `convert-core`、`format-docx`、`format-pptx`、`format-xlsx`、`format-pdf-docling`；HTML/Markdown 到对应阶段再加。每项先验证实际导入闭包，所列 extras 不是已经验证成功的安装命令。底层 core 的版本及传递依赖也必须锁定。

不选 `standard`、`all`、`models-*`、`feat-ocr-*`、`feat-chunking`、`extract-core`、`format-audio`、`format-video`、`service-client`、HTML 浏览器渲染。不启用上游外部插件发现、默认本地模型管线或第三方自行下载。外部模型统一走 Knoa Provider，不改造 Docling 的全部标准模型阶段。

上游 API 若依然强制导入不允许的组件，先找同系列已发布可用版本或小范围上游修复；不得用 `--no-deps`、假模块或未记录 monkey patch 绕过。若仍无法保持边界，停止该格式准入并重新评估其替代方案，不同时留下多个生产引擎。

### Excel 补充层的有限职责

Docling 当前读取缓存值，因此补充层是必要设计，而非未来可选修复：

1. 针对同一份不可变 XLSX，以保留公式和读取缓存的方式分别获取原始字段，保留 A1、工作表、类型、数字格式、合并与隐藏信息；不执行公式或外链。
2. 以工作表身份、区域锚点、局部行列关联 Docling 表格。上游的工作表“page”及 bbox 必须转成 sheet_range，不能当物理页或像素区域。
3. 没有缓存的公式单元格仍输出公式和 `cached_value=null`；即使上游把它当空单元格，也不能丢弃。没有被上游分区包含的原始单元格独立保存，不强行归入某表。
4. 不根据重复文本猜测合并关系；不能唯一关联时保留独立原始证据并记录问题。显示文本无法精确重建时保留 number_format 与原值，不伪造 Excel 显示效果。

这个补充层不复制 Docling 的区域发现、图表组织或整套 workbook backend。默认只接一套文档引擎，避免 Docling 与 Unstructured 等同时解析再做复杂投票。

## 4. 项目结构和内部边界

职责分区已落在标准 src/knoa_parse 命名空间，一个发行项目；原 packages/apps 文档目录已迁移到相应源码目录，避免维护两套结构。

```text
src/knoa_parse/apps/
  api/                  HTTP 入口
  cli.py                已实现初始入口，复用应用服务
  worker/               注册、调度、租约、子进程和能力装配
src/knoa_parse/
  core/                 来源、产物、任务、错误、契约与少量接口
  parsers/              按资料类型编排；13 个家族保持 planned
  engines/              一个 Docling 转换适配与结果映射
  enrichment/           上下文选择、请求预算、增强与证据关联
  processors/           媒体/容器操作和有限原始字段补充
  providers/            外部能力协议及选定供应商适配
contracts/              版本化 JSON Schema 与示例
  ...                   保留旧版，新版通过显式版本索引加入
evals/                  合成样例、golden、能力/来源/资源评测
```

依赖规则：core 不认识上游；parsers 仅调用 core 定义的接口；engines 封装上游转换；enrichment 不依赖特定格式引擎；processors 不含模型；providers 不含格式编排；apps 装配实现。不要再分一套与上游一一对应的包结构。

首版内部只需四类能力接口（名称为设计，不是已发布 API）：

- `Parser`：探测、计划与执行资料家族流程。
- `DocumentEngine`：对受支持文件执行指定的无模型转换并返回 EngineResult。
- `Processor`：按明确操作处理媒体、容器或补充原始字段。
- `Provider`：声明能力、提交/查询/取消外部请求，返回标准单元结果。

EngineResult 是内部对象：结构块、定位、产物、issues、上游运行信息；其不可避免的供应商字段只存受控原始 artifact，不进入公共 schema。不要为四个接口建设动态插件平台。

## 5. 统一证据契约

按 [结果模型](result-model.md) 落地新的 `0.2.0-draft.1`，保留 `0.1.0-draft.1` 及回归。升级前先用真实/合成产物核对表达能力，新版本名称仍是计划。主仓独立评审消费迁移后显式同步，本轮不改主仓快照。

核心对象为 SourceVersion、Artifact、ContentBlock、Locator、Derivation、Coverage、Issue、ProviderInvocation。

- 内容：标题/段落、表格及单元格、图片、转录/字幕、场景、模型说明。模型说明与原生/识别证据分开，关联输入 block IDs；不覆盖原文。
- 来源：每个块指向明确 artifact。支持原文字符、页区域、工作表范围、幻灯片/形状、文档节点、时间片段及容器链。
- 精度：区分原件可精确定位、派生产物可精确定位、估计位置和不可定位。保留 Docling 的 self_ref 只证明可定位到其 JSON 节点，不等于原 DOCX 节点或 PPT shape ID。
- 结构：保留原始顺序与已知的阅读顺序状态；NativePdfPipeline 不确定的顺序必须标记 unresolved，不能包装成确定阅读序列。
- 原始结果：保存上游 JSON 和必要二进制 artifact，映射直接从结构化结果进行，不经 Markdown/content_list 有损中转。
- 完整性：记录每页/工作表/音轨/时间段的完成、跳过与失败，以及请求目标对应的缺口。数据块可以是完整的，但不意味着整个文件已完整处理。

获取不到原件精确定位时，不能伪造。允许返回指向完整派生结果的定位并明确精度/缺口；若请求要求原件精确定位，则相关目标失败或部分完成。Schema 必须能表达这一区别，而不是以一个 page 字段兼容所有类型。

## 6. 请求、任务与外部服务

### 对外入口

建议首版 API：

| 入口 | 职责 |
| --- | --- |
| `POST /v1/sources` | 上传并固定来源摘要，返回 source_version_id；不接任意服务器路径 |
| `GET /v1/capabilities` | 返回当前安装、配置且验收通过的格式/目标/服务能力 |
| `POST /v1/jobs` | source_version_id、目标、选项、预算与幂等键，返回 job_id |
| `GET /v1/jobs/{id}` | 状态、阶段、单元进度与错误；未知总量不伪造百分比 |
| `POST /v1/jobs/{id}/cancel` | 标记取消、停止本地子进程并尝试取消远端任务 |
| `GET /v1/jobs/{id}/result` | 版本化结果清单及 artifact 引用 |
| `GET /v1/artifacts/{id}` | 经过来源/任务授权检查的产物读取 |

CLI 提供 parse、status、result、capabilities，并复用同一应用层。对外不出现 Docling class、MinerU content_list 或上游开关名称；诊断可显示引擎版本和许可来源。

### 目标与执行

初始只定义可验证目标：`native_extract`、`document_understanding`、`transcribe`、`video_understanding`；后续网页正文目标再开放。不设自动兜底到所有框架的模式。

- native_extract：提取原件中已有结构，明确不包含模型补全；扫描正文没有被读取时仍要记录缺口，不能因存在页眉文字而宣称整页可读。
- document_understanding：计划需要的 OCR、布局/表格等能力；缺少服务配置在外发前报缺失，显式 best_effort 才允许降级为部分结果。
- transcribe：转录音轨，字幕与转录分别保留；不能标成完整视频理解。
- video_understanding：组合场景/视觉、音轨和字幕；按采样记录覆盖范围，不保证理解每帧。

任务状态建议 queued、running、succeeded、partial、failed、cancelled；它们属于 job 协议，不直接塞进旧版 ParseResult 的 completed/partial/failed。阶段及每单元状态独立记录，以防跨阶段重试重做全部工作。

SQLite 保存任务、单元、租约、artifact 元数据与外部调用账目；文件存储采用内容摘要和受控路径，写入完成后原子发布。崩溃恢复首先核对已落盘产物和远端请求 ID，不盲目重新计费。CLI/API 同时运行通过事务租约保证任务不会被重复领取。

### Provider 边界

保留 OCR、ASR、Vision、DocumentAnalysis、TextModel 五类能力协议，但首版不同时安装五套供应商 SDK。按实际目标接入一个可满足需求的服务；DocumentAnalysis 已提供 OCR/表格时，不再无条件追加 OCR 调用。

能力声明包括输入格式、页数/大小/时长限制、语言、坐标单位、时间戳精度、同步/异步、幂等和取消支持。大文件输入通过受控上传或受限临时引用传递，不由解析器自行重新下载来源。

结构错误、429、超时和服务永久失败分别处理；远端请求超时但状态未知时优先查询，服务不支持查询/幂等则显式记录 unknown，不能无限重提。费用未知不填零；自动回退只使用显式允许的已配置服务，并重新核对预算。

## 7. 控制重量与源码范围

| 控制项 | 首版边界 | 验证方式 |
| --- | --- | --- |
| 综合引擎 | 默认恰好一个；同一格式/目标只有一个主实现 | 注册清单和依赖审查；新增替代品必须说明替代或独特增益 |
| 本地模型 | 权重、推理、下载器及运行时回退均不允许 | 锁文件/依赖图、构建产物、冷启动与网络行为检查 |
| RAG 基建 | 不带 LightRAG、向量库、图谱、embedding、Agent 框架 | 锁文件与导入边界检查，不靠“没有调用”代替 |
| 依赖分组 | base / documents / media / web-maintext / provider-specific | base 不反向依赖可选组；分别构建、启动和卸载验证 |
| 媒体依赖 | FFmpeg/ffprobe 与一个 headless 检测分发 | 不同时安装多种 OpenCV 分发；不选 MoviePy extras |
| 渲染与长尾 | LibreOffice、浏览器、JVM 不进入默认安装 | 部署清单核对；有明确功能和测试后专项引入 |
| 源码复制 | 当前计划为零；必要时只迁入一个可说明的模块闭包 | 固定 commit、原文件/依赖/测试清单、许可、改动说明 |
| 产品组件 | 一套任务和配置、无上游 UI/服务端/资料库 | 启动进程与端口清单、安装文档检查 |

包里未调用的普通源码不需要为了“零冗余”全部删掉；这种裁剪容易制造长期 fork。重点是避免无关传递依赖、后台服务、模型和需要本项目维护的复制代码。普通解析库并非禁用，但每个新增高层模块必须说明为何已有能力不能满足。

首次安装实验记录各依赖组的解析清单、wheel/安装体积、冷启动时间、峰值 RSS、临时存储和任务吞吐；不以单个 wheel 大小冒充完整安装大小。首轮实测见 evals/baselines/2026-10-15-documents.json，包含完整环境和单进程实验的范围，不是通用性能承诺。以后新增组件必须记录相对基线增量，无法解释收益的依赖拒绝合入。

运行时每任务配置上传大小、解包字节/条目/递归、页数、时长、抽帧数、并发外部请求、超时和费用上限。默认值通过首批资料基线确定；发布前必须给出明确值和配置样例，不能以“可配置”代替限制。

## 8. 评测与准入

建立小型合成 golden 集，覆盖真实能力边界；不使用私有资料，不把上游 benchmark 直接当本项目成绩。各格式至少覆盖普通、复杂结构、缺失/损坏和资源边界四类案例，详细场景见 [evals](../evals/README.md)。

重点判据：

1. 结构保存：正文、表格合并、备注/脚注、图表数据、关系不被 Markdown 中转压平；预期差异都有原因记录。
2. 定位正确：重复段落不串联，Excel 工作表坐标不冒充页区域，PPT 形状/备注分离，视频时间与原 PTS 对应。
3. 语义保存：公式没有缓存时不丢公式、不填零；隐藏字段有标记；图表数字和模型描述分开。
4. 完整性：扫描页、缺音轨、外部缺段、嵌套附件失败可见；失败不会转成普通文本或空成功。
5. 无本地模型：全新环境、空模型缓存、网络受限时原生路径成功；模型路径只报外部能力缺失。结合依赖与执行记录，不能只用断网测试证明没有预装模型。
6. 可恢复性：取消/崩溃后产物不损坏、任务不双重领取、重试不无界重复计费。
7. 资源：记录每组的安装与运行基线；超过配置上限受控结束，不拖垮 API。

对确定性合成 golden 的必需字段要求精确一致；复杂阅读顺序、OCR、表格恢复与 ASR 等真实效果建立人工标注后另设指标，不能预先声称任意统一通过率。上游模型换成外部服务后重新测量，原项目成绩不继承。

M0 先解决最可能推翻选型的问题，避免先写大量适配代码再发现运行依赖或来源信息不符合要求。文档、音频、视频分别发布能力，不用等待所有家族齐备。

## 10. 升级、退出与当前状态

依赖采用固定版本和 hash；源码迁移若发生，另记录原仓库、固定提交、路径、许可、测试来源和差异，保留归属。项目自身许可证尚未定，分发前确认与已选依赖兼容。FFmpeg 以实际构建清单核对许可，不把所有构建统一标为同一种许可证。

升级只更新选定模块并复跑相同 golden 与资源基线；不自动启用新增上游格式、模型或插件。升级失败回到上一锁版本和适配器，不改变公共结果契约；已产生结果继续可读。替换引擎先在评测中对照，生产路由仍保持单一主实现。

实施进度与当前限制见 [初始实施记录](implementation-status.md)。当前文本/JSON 最小闭环已通过本地回归，Docling 与 Excel 补充的初始路径已有验收；媒体、真实服务和更广泛的格式特性仍待开发。
